# API リソースを追加・変更する

前提：書き込みはすべて `/api/v1`（OpenAPI 準拠）と共通サービス層を
通す（AGENTS.md の約束）。画面専用の POST ハンドラは作らない。
確認範囲の漏れを防ぐため、以下の手順を上から順に行うこと。

## 手順

1. **サービス層にロジックを置く**（`web/app/main.py` の services 節）
   - 導出（約定状態の自動判定、売却損益の自動計算、月あたり所得の
     自動算出など）はサービス層に1か所だけ。API ハンドラや画面に
     複製しない。
   - 削除は rowcount の有無を返し、対象なしを呼び出し側で 404 に
     できるようにする。
2. **Pydantic モデルを定義する**
   - 入力は `<Resource>In`、出力は `<Resource>Out`。型・必須・
     nullable は DB の実態に合わせる（金額は float、日付は date）。
   - 配当のように自動取得のみが正の項目は入力モデルに含めない
     （編集不可を型で表す）。
3. **ルートを追加する**
   - パスは `/api/v1/<複数形>`。`response_model` と `tags` を必ず
     付ける（OpenAPI に載ること自体が仕様の一部）。
   - ステータスコードの規約：作成 201、削除 204、対象なし 404、
     入力不正は Pydantic の 422 に任せる。
   - コミット後に `emit_event` で動作ログを残す（既存のイベント
     命名に合わせる）。
4. **画面を API 経由にする**
   - `base.html` の `apiJson()` と `strOrNull` / `numOrNull` /
     `intOrNull` を使って fetch で呼ぶ。成功時は再読み込みして
     サーバ描画の表示と一致させる。
5. **テストを足す**
   - `tests/test_api.py`：`/openapi.json` にパスとスキーマが載る
     こと、参照系、バリデーション（422）、対象なし（404）。
   - `tests/test_endpoints.py`：導出と書き込みの往復
     （作成→参照→削除）。
   - run-tests スキルで実行し、分岐カバレッジ 95% を維持する。
6. **文書を更新する**
   - DESIGN.md の Web API の節にエンドポイントと仕様（導出の
     ルール、編集不可の項目など）を追記する。
7. **デプロイして本番で確認する**
   - `docker compose up -d --build web` のあと、全画面 200、
     `/openapi.json` に新しいパスがあること、実データの参照が
     返ることを確認する。
   - 書き込みはダミーデータで作成→削除の往復まで確認し、
     件数が元に戻ったことを確かめる。

## 注意

- `/api/fetch-status` は取得状況ポーリング専用の旧来エンドポイント
  で、/api/v1 の規約の対象外（画面内部用）。
- 認証は現状なし（ローカル NW のみで運用する前提）。外部連携を
  始めるときは、先に認証と公開範囲を決めること。
